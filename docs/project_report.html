01

Introduction

Buying a car is a constrained search problem dressed up as a conversation. A shopper rarely knows the catalogue; they know a budget, a body style, a number of seats, and a vague sense of priorities — “something with a big boot,” “the cheapest automatic.” A keyword search engine cannot interpret that, and a language model asked to answer from memory will confidently invent prices.

This project builds a conversational recommender that does neither. It retrieves real rows from a 150-vehicle dataset, filters them against constraints extracted and validated in Python, and asks a locally-hosted language model only to write prose over facts it has been handed. The system runs end to end on a 16 GB Windows laptop with no GPU and no cloud API.

Objectives

  • Combine sparse (BM25) and dense (embedding) retrieval so both exact model names and loose semantic descriptions are answerable from one index.
  • Extract structured constraints from natural language, and enforce them with deterministic Python filters rather than trusting the model.
  • Degrade honestly: when nothing satisfies the request, relax constraints in a defined order and tell the user which requirement was dropped.
  • Ground every generated sentence in retrieved data, and never present a synthetic artefact as a real vehicle fact.

Design constraints

Several decisions were fixed before implementation and held throughout, which shapes much of what follows. No orchestration framework was permitted — no LangChain, no LlamaIndex — so every stage is raw Python over sentence-transformers, faiss-cpu, rank-bm25 and ollama. Inference is local and CPU-only. The source CSV is treated as immutable. Four rules were non-negotiable:

  • The language model never directly controls metadata filtering; all filter logic passes through Python validation first.
  • The cross-encoder never runs over the full 150-vehicle set — only over a bounded candidate list.
  • Hypothetical (HyDE) descriptions are synthetic and are never shown as real.
  • Answers explicitly declare their retrieval mode and never claim an unverified constraint was met.

Contributions

Beyond a standard RAG pipeline, this work contributes a four-mode retrieval strategy with ordered constraint relaxation; a direct-metadata-sort path for superlative queries, where embeddings are structurally incapable of being correct; an LLM-independent comparison table that guarantees numeric accuracy regardless of what the prose says; and a measured latency study that locates the real bottleneck of small-model local RAG.

02

Literature Survey

Retrieval-augmented generation sits on three decades of information retrieval research. The survey below traces the specific lineage this system draws on, and states how each idea is used here rather than merely citing it.

Sparse retrieval

BM25 (Robertson & Zaragoza, 2009) remains the strongest non-neural ranking function and a standard baseline. It scores documents by term frequency saturation and inverse document frequency, which makes it excellent at exact lexical matching — a model name such as “Porsche Cayenne” — and blind to paraphrase. The rank-bm25 implementation of BM25Okapi is used unmodified.

Dense retrieval

Sentence-BERT (Reimers & Gurevych, 2019) made bi-encoder sentence embeddings practical by training siamese BERT networks to place semantically similar text near one another in vector space. Dense Passage Retrieval (Karpukhin et al., 2020) demonstrated that such embeddings can outperform BM25 on open-domain question answering. This project uses all-MiniLM-L6-v2, a 384-dimension distilled model, indexed with FAISS (Johnson et al., 2019; Douze et al., 2024) using an IndexFlatIP exact inner-product index — at 300 vectors, approximate search would trade accuracy for a speed-up that is not needed.

Hybrid fusion

Sparse and dense retrieval fail in complementary ways, which motivates fusion. Reciprocal Rank Fusion (Cormack et al., 2009) combines rankings without tuning; weighted score fusion instead normalises and blends raw scores, requiring a mixing weight but preserving score magnitude. This system uses min–max normalisation followed by weighted fusion, with the weight swept empirically (Section 4).

Reranking

Bi-encoders embed query and document independently, which is what makes them fast and also what limits their precision. Cross-encoders (Nogueira & Cho, 2019) jointly encode the pair and score it directly, giving substantially better relevance judgements at a cost that scales with the number of pairs. The standard remedy — retrieve broadly, rerank narrowly — is adopted here with a hard architectural limit of 30 candidates, using a ms-marco-MiniLM checkpoint trained on MS MARCO (Nguyen et al., 2016).

Retrieval-augmented generation and query transformation

Lewis et al. (2020) introduced RAG as joint retrieval and generation for knowledge-intensive tasks, establishing grounding as an alternative to parametric recall. Two later refinements are implemented and evaluated here: HyDE (Gao et al., 2023), which generates a hypothetical answer document and embeds that instead of the query, closing the vocabulary gap between questions and documents; and LLM query rewriting (Ma et al., 2023), which restates a conversational utterance as a standalone search query.

Local small-model inference

The generator is Qwen3 4B (Qwen Team, 2025) at Q4_K_M quantisation, served by Ollama. Qwen3 is a hybrid-reasoning model that emits an explicit thinking phase by default — behaviour that is valuable for hard reasoning and ruinous for latency on a CPU. Suppressing it reliably required grammar-constrained decoding via a JSON schema, a technique that also guarantees parseable structured extraction. This interaction between reasoning modes and decoding constraints proved to be one of the more consequential engineering findings of the project.

Methodology and Implementation

The system is built in thirteen sequential phases, each with a working checkpoint, plus one extension beyond the original specification. Implementation totals 3,701 lines across 56 source modules, with 2,802 lines of tests across 26 test files.

Stages 3, 5, 6 and 7 are pure Python and NumPy; the four LLM calls are the entire latency budget, as Section 4 quantifies.

Ingestion, enrichment and chunking

The source CSV carries 150 rows and 34 columns, spanning 26 brands, prices from ₹3.18 lakh to ₹950 lakh (median ₹54.78 lakh), 10 fuel types and seating capacities from 2 to 8. The file is never modified. A normalisation layer parses composite text fields into typed metadata — price bands, mileage and engine-displacement ranges, boot space, ground clearance, top speed, transmission availability — and an extensible enrichment interface derives fields the raw data only implies, most notably body type, which is inferred from dimensions and ground clearance.

Correctness note

The first body-type heuristic ordered its checks by ground clearance before length, which misclassified several hatchbacks as SUVs and three hatchbacks as sedans. The rule was corrected and then verified exhaustively against all 150 rows rather than spot-checked — a reminder that derived metadata is a correctness surface, not a convenience.

Each vehicle is split by a custom recursive character chunker into exactly two chunks: a product_overview and a features chunk, giving 300 chunks averaging 331 characters. Two chunks per vehicle keeps each unit topically coherent while ensuring a vehicle is retrievable by either its positioning or its specifications.

Query understanding and the validation boundary

Constraint extraction asks the model for JSON conforming to a schema, then discards anything that does not validate. Two schemas exist: a 7-field core schema and a 19-field extended schema, selected by a cheap lexical test, because grammar-constrained decoding latency scales with the number of required fields. Any failure — timeout, malformed JSON, invalid enum — falls back to regex extraction rather than to an unconstrained model.

Architectural rule

The model proposes constraints; it never applies them. Extracted values are validated against known brands, enumerated body types and transmissions, and numeric bounds before any filtering occurs. A hallucinated brand becomes a dropped constraint, not a wrong result set.

An early failure illustrates why the boundary matters: asked to “suggest cars of bmw,” the extractor invented seventeen unrequested fields and the system recommended a Volvo. Making the schema fields optional did not fix it; an explicitly anti-inventive prompt did. A separate defect had the superlative detector matching \w+est inside the word “sugg⁠est.”

Retrieval modes

Retrieval resolves into one of four declared modes, and the mode is always surfaced to the user:

  • Exact — every extracted constraint is satisfied.
  • Relaxed — constraints are dropped in a configured order, softer preferences first (top speed, boot space, ground clearance, mileage, engine size) and budget later. Price widens by real dataset quantiles rather than an arbitrary percentage. Every dropped constraint is reported.
  • Fallback — no constraint could be verified; results are semantic matches only, and the answer says so.
  • Superlative — “cheapest,” “fastest,” “biggest boot.” Handled by a direct Python sort over metadata, bypassing retrieval entirely.
Why superlatives bypass retrieval

Embeddings and BM25 have no notion of numeric magnitude. The genuinely cheapest vehicle may not appear in the top-K at all, so no amount of reranking can rescue the answer. Sorting metadata directly is not an optimisation here — it is the only construction that can be correct.

Generation and its guardrails

The generation prompt carries the retrieval mode, both chunks for each returned vehicle, and a precomputed comparison table in which each column's extreme is already tagged (“cheapest,” “largest boot”). Precomputing extremes means the model reads comparisons instead of deriving them — it cannot get arithmetic wrong if it never does any. This followed an observed failure in which the model reported two boot volumes “respectively,” swapped, and called a 515 L boot less practical than a 480 L one.

Four detectors gate the output: meta-narration, context echo, incompleteness, and surviving prompt placeholders. A failing answer is regenerated through a slower unconstrained path; if that fails, the original is kept rather than replaced with an error.

Prompt contamination

The prompt originally contained a worked example. Its “7-seater” framing leaked into answers for queries that never mentioned seats. Replacing the example with bracketed placeholders simply produced a new leak — “For exactly what you asked for, the BMW 3 Series…” — the instruction text itself with brackets stripped. Worked examples were removed entirely. Whatever enters the prompt as an example leaves it as output.

Hybrid fusion beats both of its components on every metric, which is the central result: BM25 alone reaches 0.215 P@K, dense alone 0.271, and their fusion 0.285, with MRR rising from 0.453 and 0.461 to 0.517. The two methods fail on different queries, and combining them recovers both.

The refinements are more equivocal, and reporting them honestly matters more than reporting them favourably. HyDE achieves the best MRR (0.531) and ties the best recall (0.492) — but costs 11.5 seconds, roughly 640× the hybrid baseline. Query expansion produces the best success rate (0.706) at 8.1 seconds. Both are implemented and available but deliberately left out of the default path; the measured gain does not justify the latency.

The cross-encoder result is genuinely mixed. It improves recall (0.469 → 0.492) and NDCG (0.471 → 0.492) while reducing precision (0.285 → 0.235) and success rate (0.647 → 0.588). It surfaces more relevant vehicles overall but is less reliable at putting one in the top position on this query set. At n = 17 with draft labels, this difference should be treated as suggestive rather than settled.

The variance between identical-sized prompts is the most actionable finding in the study. Ollama reuses a key-value cache when a prompt shares a prefix with the previous request, and the difference is not marginal:

  • ~400-token prompts: 13.8 s, 10.9 s, then 0.6 s, 0.6 s, 0.6 s, 0.6 s — a 23× spread at constant size.
  • ~800-token prompts: 21.7 s, then 0.6 s.
  • ~1,300-token generation prompts: 46.7 s, 39.6 s, 42.9 s — effectively never cached, because the retrieved-vehicle context differs on every query.

The shared system prompt caches after the first few calls; the per-query context block cannot. That fixed ~40 s of prompt evaluation is paid on every single request. The generation prompt decomposes as 916 characters of system prompt, 1,979 characters of vehicle text (two chunks each for three vehicles) and a 685-character comparison table — 3,882 characters, about 1,213 tokens.

Failure analysis

Seven of 21 runs (33%) produced no recommendation, returning instead the graceful fallback text — a list of matching vehicle names with no commentary. Every one of the seven was a ReadTimeout at exactly 150.0 s, the configured generation ceiling. Two query types failed all three times; one failed once.

Repeating each query three times isolates the mechanism. The failures are not random, and they are not spread evenly: they track almost perfectly with whether the quality detectors fired and triggered a regeneration.

Path takenAnsweredFailedFailure rate
3 calls — no regeneration1019%
4+ calls — regeneration fired4660%

A turn that triggers regeneration is roughly seven times more likely to fail than one that does not.

Root cause: the regeneration path is unbounded

When a quality detector rejects the first answer, the system retries through chat_long_form — deliberately unconstrained, with no JSON schema and the model's thinking phase left enabled. Nothing bounds how much it emits: the Ollama call sets only temperature, and no num_predict ceiling is configured anywhere.

The clearest evidence is the largest decode that did finish: 891 tokens in 142.6 s, clearing the 150-second wall by seven seconds, in response to a prompt asking for three to six sentences. Runs that emitted marginally more simply hit the wall. At the measured 6.2–7.8 tokens/s, a 250-token cap would bound decoding to roughly 32 s and convert every one of these timeouts into an answer.

This also reframes the fix. Capping output is necessary, but the regeneration trigger is itself worth revisiting: the system currently discards a delivered, readable answer and gambles a 150-second retry on producing a better one — a gamble it loses 60% of the time.

Remediation and re-measurement

The diagnosis above was acted on and the profile re-run under identical conditions. Generation now carries a token ceiling, the regeneration path has its own larger budget because reasoning tokens count against that ceiling too, a response truncated mid-JSON is salvaged rather than leaked to the user, and prose that names none of the retrieved vehicles is replaced by the real shortlist.

Attribution: the machine, not the code, drove the speed

It would be easy to credit the token ceiling for the whole improvement. The data does not support that. A token cap cannot change tokens-per-second, yet decode throughput rose 57% and prefill 139% — those are machine effects. The decisive check is the three query types that never reach the ceiling at all: superlative, multi-constraint and unsatisfiable still improved 38–41%, with no contribution from the code change whatsoever.

The honest split: the restart bought the speed; the cap bought the reliability. The ceiling's contribution is bounding the runaway generations — worst-case output fell from 891 tokens to the cap — which is what removed the timeouts.

Two regressions the fix introduced, and what they taught

A single shared ceiling broke two things that only measurement caught. Because chat_long_form runs with thinking enabled and reasoning tokens count against num_predict, the model spent its entire budget thinking and returned empty content on 3 of 3 runs — worse for the user than the timeout it replaced. Separately, a ceiling can stop the model mid-JSON, and the old error branch returned the raw text, leaking 1,275 characters of {"result": "... verbatim.

Both are now fixed, but the lesson generalises: a fix aimed at one failure mode can create another that the original metric does not measure. The success check in the first profiling script tested only for the timeout message, so it scored those empty answers as successes and reported 21/21. The real figure was 18/21.

Accuracy: the price-basis defect

Separately from latency, re-reading the generated answers surfaced a correctness problem that no timing metric would ever show. Every vehicle's price_lakhs is its starting price — verified, it equals Price_Min_Lakhs for all 150 rows — so a budget filter matches the entry variant, not the whole model. Ten vehicles have a base under ₹15 lakh and a top variant above it; the Tata Safari spans ₹14.69–21.45 lakh. The system was presenting ₹14.69 lakh as simply what the car costs.

The filter is unchanged — matching on starting price is the correct reading of “cars under ₹15 lakh.” What changed is the claim built on top of it: the context block now states the basis, and the prompt requires “starts at” over “priced at.” Answers now read “Hyundai Verna starts at ₹9.11 Lakh … The Mahindra Thar starts at ₹10 Lakh.”

This also resolved a contradiction the model had been visibly deliberating over: the context labelled a result EXACT while showing a range above the budget, and that reasoning leaked into the answer (“…which is over 15 lakh, so it doesn't meet the requirement. Wait, the…”). A latency symptom with an accuracy cause.

Fact-checking the answers against the dataset

With the pipeline finally answering every query type, each generated claim was checked against the source CSV rather than read for plausibility. Three were false, and two of them originated in this project's own Python rather than in the model.

False claim producedWhat the data saysOrigin
“it offers the most seats (5)”Two vehicles tie at 5tagging code
“no boot space”Boot space is absent, not zerotable rendering
“the Yaris has better fuel efficiency”Yaris 18.0 vs Verna 25.0 kmplmodel

The first two are the more serious: the prompt instructs the model to trust the table's marks, so a wrong mark becomes a wrong answer with the model behaving exactly as told.

A tie is not a winner

The superlative tagger took min() and max() over each column, and both return the first row holding that value. With two five-seaters and one four-seater, the first five-seater was silently labelled “most seats.” The model then repeated it as fact, correctly following instructions. Only uniquely-held extremes are marked now, with a regression test.

The wider point: the comparison table was introduced precisely so numbers could not be garbled by generation. That reasoning holds only while the table itself is right — moving a claim into Python makes it authoritative, which raises rather than lowers the cost of a bug in it.

The missing-value case is the same principle. Rendering an absent measurement as “N/A” invited the model to read it as zero and report “no boot space” for a vehicle whose boot simply is not in the dataset — turning missing data into a confident claim of absence. It now renders “not recorded.”

The third is the model's own: inverted pairwise comparatives. The existing rule governed superlatives (“cheapest,” “largest boot”) and said nothing about comparisons between two cars, which is exactly where the errors occurred. Unmarked comparisons are now forbidden outright rather than asked to be accurate — every extreme is already computed in Python, so the model never needs to derive one.

After the fixes, “cars under 15 lakh” verifies clean on every checkable claim: largest boot (480 vs 476 L), best fuel efficiency (25 vs 18 vs 15.2 kmpl), higher price, fewer seats, and better top speed (230 vs 200 km/h). Two minor defects persist in the SUV query: the word “respectively” still appears despite an explicit ban, and boot space is compared against a vehicle whose boot is unrecorded.

Instruction literalism

The narration fix took two attempts. Phrased as “your first word is the name of the car,” both test queries returned a bare Mahindra Thar — 13 characters, no recommendation. Scoping the rule to the first sentence, while keeping “3-6 complete sentences” dominant, produced correct prose. Constraining where something appears is safe; phrasing it as what the reply is replaces the content. The same literalism had already appeared earlier in this project, when a worked example's “7-seater” framing leaked into unrelated answers.

Verification

The full suite is 308 tests across 26 files, all passing, with no skips. It now completes in roughly 4–8 minutes, down from about 70 before the remediation and the restart. The live model tests genuinely execute: the Ollama availability probe originally allowed 10 seconds, while a cold model load was measured at 70.4 s, so whenever the model had been evicted every language-model test skipped silently. A silent skip is worse than a failure — it presents as coverage while providing none.

The suite also caught what review did not. A grounding guard written to require the full vehicle name (“Porsche Macan”) was rejected by a test whose fixture said “the Macan” — genuinely grounded prose. Had that shipped, it would have silently discarded good answers in production, since both the model and real customers routinely drop the brand.

Validity caveats

Ground truth is a draft. The 27-query evaluation set was drafted by the coding agent and is explicitly marked as requiring human review before its numbers are treated as final. Only 17 queries carry usable labels. All retrieval metrics above inherit that caveat.

Latency is n = 3 per query type (21 runs), single machine, warm model. Three repetitions establish which query types fail reliably but remain too few for confident interval estimates; the spread within a type is real, with multi-constraint ranging 51.9–117.9 s. The machine had 4.0 GB free of 15.6 GB at the start of the run against a ~3.4 GB model, so memory pressure cannot be fully excluded as a contributor to the slower tail.

05

Advantages and Limitations

Advantages

  • Fully local. No API key, no per-query cost, no data leaving the machine. The catalogue and every query stay on the laptop.
  • Numerically trustworthy. Comparison tables and superlative rankings are computed in Python from metadata. The model cannot garble a figure it never calculated.
  • Honest degradation. Four declared modes mean the user is told when a constraint was relaxed or when nothing could be verified — instead of silently receiving plausible-looking wrong results.
  • Hybrid retrieval measurably works. Fusion beats both components on every metric at 18 ms, the clearest positive result in the evaluation.
  • Hallucination containment by construction. The model proposes constraints but never applies them, so an invented brand degrades to a dropped filter rather than a wrong answer.
  • Genuinely tested. 307 passing tests including live-model paths, with the instrumentation to prove they ran.

Limitations

  • Latency remains outside conversational expectations. A 43.1 s median and 118.6 s worst case after remediation are far better than before, and still far too slow for a chat interface.
  • Answer accuracy is verified only by spot-check. Claims were fact-checked against the CSV for two query types, not systematically across the eval set. Two minor defects persist: a banned word (“respectively”) still appears, and one comparison is made against an unrecorded value.
  • Evaluation rests on draft labels. 17 labelled queries, agent-authored, pending human review. Differences under ~0.05 should not be read as real.
  • Corpus is small and static. 150 vehicles, 300 chunks. Nothing here has been tested at a scale where exact FAISS search or in-memory BM25 would stop being appropriate.
  • Seating and body type extract unreliably (66.7% and 88.9%) — precisely the inferred rather than stated fields.
  • HyDE and expansion are measured but unused, their accuracy gains not justifying 8–11 s of added latency.
  • Single-machine results. Every figure reflects one CPU-only Windows laptop.
06

Conclusion and Future Scope

The system demonstrates that a grounded, constraint-aware conversational recommender can be built from primitives alone — no orchestration framework — and run without a GPU. The retrieval architecture is sound and fast: hybrid fusion outperforms both BM25 and dense retrieval on every measured metric while adding 18 milliseconds, and the constraint validation boundary keeps a small, hallucination-prone model from ever directly controlling what the user sees.

The honest conclusion is that retrieval was never the hard part. Every retrieval stage combined costs under 1.4 seconds in all 21 profiled runs. Well over 99% of each query is local language-model inference. The engineering difficulty in small-model local RAG lies in prompt economics and output control, not in the search stack.

The repeated profile sharpened this into a specific defect, since fixed. The system's own quality guardrail had been its largest source of failure: when a detector rejected an answer, the unbounded retry it triggered exceeded the timeout 60% of the time, so a third of all queries returned no recommendation at all. Bounding generated tokens eliminated every timeout.

Three lessons survive the specifics. Measure the fix, not just the bug — the token ceiling cured the timeouts and introduced empty answers, which the original success metric scored as passes. Separate the variables — most of the apparent speed-up came from restarting the machine, not from the code, and only the query types that never touch the ceiling revealed that. And the defect that mattered most was never visible in a timing chart: the system was quietly presenting a car's entry-variant price as its price, which no latency measurement would ever surface and no user would forgive.

Future scope

The following are ordered by measured impact, and each addresses a specific finding above rather than a general aspiration.

  • Assert answer accuracy in the test suite. The three false claims found here were caught by reading answers against the CSV by hand. A test that checks generated comparatives against metadata would catch the next one automatically.
  • Reconsider when regeneration fires. It is invoked on roughly half of all turns. Narrowing the detectors would avoid paying for a second generation on answers that were adequate to begin with.
  • Trim the generation context. The features chunk contributes roughly 1,168 of 3,882 prompt characters while the comparison table already carries the specifications that matter — an estimated 11 s saving per query, to be validated against answer quality.
  • Merge query understanding and transformation into a single call, removing one full round trip from every request.
  • Stabilise the extraction schema. Alternating between the 7-field and 19-field schemas defeats the prefix cache; committing to one trades tokens for cache hits, and which wins is an empirical question worth measuring.
  • Complete the human review of the evaluation set, so retrieval metrics can be quoted as results rather than as machinery validation, and re-run the fusion sweep on reviewed labels.
  • Revisit the cross-encoder's role, given that it currently trades precision for recall on this query set.
  • Phase 14 — Langfuse tracing, deferred by design until the pipeline worked end to end, would replace the ad-hoc instrumentation written for this study.
  • Hardware or hosting. At ~1,861 prompt and ~270 generated tokens per query, a hosted model or any GPU would bring responses into the 3–7 second range. That trades away the offline, zero-cost, private-by-construction properties that motivated the local design, and would mask rather than fix the unbounded-decoding defect — so it is a deliberate trade-off, not a strict upgrade.
